    ADR-0014: Polymorphic references resolve over the concrete class closure; abstract classes get GraphQL interface types, are queryable anchors, and the manifest carries the class hierarchy¶

    • Status: Accepted
    • Date: 2026-11-10 (ratified, scope widened; proposed 2026-10-27, shape decided in the datahelix#113 decision pass, item M2)
    • Deciders: labadorf (shape 2026-10-27; scope and ratification 2026-11-10, in the datahelix#126 decision pass)
    • Related: ADR-0005 (edge-only GraphQL references — the raw *_id fallback this ADR retires); ADR-0006 (typed where: filter contract — the interface-typed filter input this ADR adds); ADR-0009 (capability manifest and QuerySpec — predicate and UNKNOWN_ANCHOR semantics change here); ADR-0011 / ADR-0012 / ADR-0013 (inverse slots — every reverse ranged on an abstract class is usable only through this ADR); issue #224 (concrete_class_closure, the inverse-edge storage half already shipped); #241 (rows lost through concrete parents and forward abstract edges — fixed by Decision 1); reel#10 (the planner anchors on abstract Sample); datahelix#113 M2, M5, R3; datahelix#57 (pending hippo_* → mosaic_* annotation rename).
    • Tracking issue: #228

    Context¶

    exposed_class_names (core/schema_typing.py:155) skips every abstract class, so an abstract class has no GraphQL object type, no collection, no manifest entry and no accessor. Three things follow, each measured on brainbank-hippo-schema 05c58aa against mosaic main:

    1. References ranged on an abstract class fall back to raw ids. GraphQLTypeBuilder (graphql/schema_builder.py:467, resolvable = slot.target_class in self.entities) keeps a raw *_id / *_ids field "as an interim" and warns at build time (schema_builder.py:612). On brain bank that is 56 fields: Diagnosis.sample, Measurement.sample, Assay.inputs, every banking process's inputs/outputs, Dataset.produced_by (→ Activity), BrainBank.assessments (→ Assessment). ADR-0005's edge-only rule is therefore violated on exactly the schema's most connected slots.
    2. The manifest marks them non-filterable. build_capability_manifest (schema_typing.py:384, predicate = slot.target_class in exposed) sets predicate=False, so QuerySpec rejects them with NOT_PREDICATE_FILTERABLE and the typed where: input omits them. The storage layer resolves inverse edges over an abstract range since #224; no transport can use them. Forward references into an abstract range are worse off: see 5 below.

    3. An abstract class cannot be an anchor. validate_query_spec answers anchor: "Sample" with UNKNOWN_ANCHOR (query_spec.py:469). A planner grounded on the manifest sees Blood, Brain, CSF and 30 more with nothing tying them to the word "sample" the user and the schema's own descriptions use (reel#10). The same gap blocks ADR-0012's flagship case: a synthesized Donor.samples → Sample resolves in storage and is unusable from GraphQL, REST or MCP.

    4. A concrete class with subclasses loses rows too (#241). A reference is resolved in its range class's own table, so a reference ranged on concrete Process whose target row lives in BankFreshBrain's table renders null in GraphQL. On brain-bank data at v0.15.0: CNSSection.producedBy null for 13 of 13 rows, Brain.producedBy 11 of 11, Measurement.person (→ Person, the row is a Donor) 1 of 1. Brain bank has 14 concrete classes with subclasses and 128 exposed forward reference fields ranged on them. This also leaves datahelix#113 M5's "Sample → producing process" broken in GraphQL.

    5. Storage handles abstract ranges for inverse edges only (#241). This ADR as first proposed said storage already resolved these edges since #224. That holds for inverse hydration. A forward count_relationship into an abstract range ignores the closure (an RNASeqAssay that hydrates 3 inputs counts 0), and an edge filter into one cannot see a leaf-table field (Unknown filter field 'sample_id'). The same gaps hit a concrete base with subclasses (an inverse listing 1 item while its count says 2).

    Abstract classes on this schema: Activity, ArrayAssay, ArrayDataset, Assessment, Association, CultureTissue, NamedThing, Quantity, Sample, SequenceDataset, SequencingAssay. Person, Dataset and Assay are concrete (datahelix#113 listed them as abstract; the reproduction corrected that), and with Process they are the concrete-parent case of item 4.

    Decision¶

    Mosaic will resolve every reference over the concrete closure of its range class, and represent an abstract class as a first-class polymorphic entity. A class qualifies when it is the range of an exposed reference or has at least one exposed concrete descendant. This covers two kinds of parent:

    • a concrete parent — a concrete class with exposed subclasses (Process with BankFreshBrain; Person with Donor): Decision 1 only;

    • an abstract parent (Sample, Activity, Assessment, …): Decisions 1–5.

    • Closure-aware resolution, for every reference. A reference (forward or inverse) ranged on class C resolves the referenced id across concrete_class_closure(C) — C itself when it is concrete, plus every exposed concrete descendant — rather than in C's own table only, and carries the row's concrete entity_type. count_relationship and edge predicates (where: to-one nesting and some/none, QuerySpec edge conditions) are closure-aware in the same way, in both SQLite and Postgres, forward and inverse alike. A nested where on such an edge accepts the slots induced on C; a slot only some descendants have is UNKNOWN_SLOT, as on an inverse edge today.

    • Concrete parent: no change to field types. The field keeps its type — the base object type (Process, Person) — and a subclass row is rendered as that base type, exposing the base's induced slots. __typename names the base, not the subclass. This fixes #241 (CNSSection.producedBy, Brain.producedBy, Measurement.person returning null) and datahelix#113 M5's "Sample → producing process".
    • Concrete parent: its own collection resolves over the closure too. A concrete parent's own collection and accessor (the GraphQL list processes and its Page/count, the SDK query(entity_type="Process"), and QuerySpec with anchor: "Process") resolve over concrete_class_closure(Process), so they list BankFreshBrain, SectionFixedBrain, … rows as well, rendered as the base object type the same way a reference is. Filters, order_by, facets and field_range on that collection apply to the base's induced slots. Each row carries its concrete type so a caller can narrow: the SDK envelope already carries entity_type (the leaf class) on every query item; GraphQL has no such field today (__typename names the base, and the per-type object types expose only id, is_available and the schema's slots), so the implementation adds a non-null entityType: String! system field to the object type of every concrete parent, naming the row's concrete class. That field is additive. To narrow, a client filters or re-queries the subclass's own collection. This is a behaviour change for existing clients: lists, page totals and counts on a concrete parent grow by the subclass rows. It must be called out in the release notes of the version that ships it.
    • Abstract parent: rendered through the interface of Decision 2.
    • GraphQL: an interface type per qualifying abstract class, carrying the slots induced on the abstract class itself, implemented by every concrete descendant's object type. A reference or inverse ranged on the abstract class resolves to the interface and returns concrete objects (__typename names the leaf). The raw-id fallback and its build-time warning are removed for this case; a reference whose target has no exposed concrete descendant stays a raw id, and the warning stays for it. Interface, not union: the shared slots (Sample.donor, Sample.sample_id, …) are the common case and must be selectable without a fragment per concrete kind.
    • A qualifying abstract class is a queryable, read-only anchor. It gets an accessor (samples), a Page type, a typed filter input built from its induced slots (ADR-0006), and search{Plural} when any descendant has a searchable slot. The collection resolves over the concrete closure, in the shape #224 gave inverse hydration: SQLite UNION ALL across per-class tables, Postgres entity_type = ANY(...). Rows carry their concrete entity_type. order_by, facet counts and field_range apply to induced slots only; a subclass-only slot is UNKNOWN_SLOT on the abstract anchor.
    • The capability manifest carries the class hierarchy. EntityCapability gains abstract: bool, parent: Optional[str] (the nearest is_a), and kinds: tuple[str, ...] (the exposed concrete closure, empty for a leaf). mosaic://capabilities and MosaicSlotInfo/hippoSchema serialize them. predicate for a reference becomes true when its target class is in the manifest, which now includes qualifying abstract classes. QuerySpec follows: UNKNOWN_ANCHOR no longer fires for a qualifying abstract anchor; NOT_PREDICATE_FILTERABLE no longer fires for a reference ranged on one. The construct-query-spec prompt gains one item: an entity with kinds is a family; anchor on it when the question is about the family, on a kind when it names one.
    • Root classes are included by the same rule, with a schema-author opt-out. A class whose closure is the whole exposed set (NamedThing) qualifies like any other; there is no built-in "skip the root" policy. Instead, two new class annotations let a schema author opt any class out:
    • hippo_anchor: false — the class is not an anchor: no abstract accessor, Page, filter input or search{Plural} is generated for it (Decision 3), and QuerySpec answers it with UNKNOWN_ANCHOR. Its interface type (Decision 2) and closure resolution of references ranged on it (Decision 1) are unaffected. On a concrete class it removes only QuerySpec anchoring; its existing accessor and write surface stay.
    • hippo_manifest: false — the class has no EntityCapability in the planner-facing manifest (Decision 4): it is not offered as an anchor, is not named as any entry's parent, and a reference ranged on it reports predicate=false. GraphQL and SDK resolution are unaffected; this hides the class from the planner, it does not remove it.

    Both default to true, are declared in hippo_ext.yaml in the class_annotation subset (so the existing annotation validator accepts them on classes only), and follow the hippo_accessor / hippo_search naming. Under datahelix#57's pending hippo_* → mosaic_* rename they become mosaic_anchor / mosaic_manifest, read under both spellings for the deprecation window like every other annotation key.

    Note (2026-11-20, platform ADR-0007 / #124): the rename landed in v0.16.0 without a deprecation window. The keys are now mosaic_anchor / mosaic_manifest, declared in mosaic_ext.yaml; hippo_anchor / hippo_manifest are not read, and a schema that still uses them fails validation with an error naming the new key. The text above is kept as ratified; read hippo_* in it as mosaic_*. 6. Writes are unchanged. No create/update input is generated for an abstract class; the abstract accessor is read-only. Ingest already dispatches on designates_type (ADR-0003).

    Implementation order¶

    1. #241's strict-xfail tests on its minimal fixture (Person/Donor, Process with a subclass, abstract Sample with two leaves, a to-many Assay.inputs), pinning each lost-row case on both adapters.
    2. Closure-aware resolution (Decision 1): references, count_relationship and edge predicates over the closure in SQLite and Postgres. The xfails flip to passes; concrete parents are done at this step.
    3. Interfaces and abstract anchors (Decisions 2–5), then the manifest hierarchy and the QuerySpec changes.

    Consequences¶

    • 241's lost rows come back: every reference through a concrete parent (128 exposed forward¶

      reference fields on brain bank) and every forward count/filter into an abstract range resolves over the closure, on both adapters, with no change to field types for the concrete case (the only GraphQL addition there is the entityType field).
    • Every brain-bank reverse ranged on Sample, Activity or Assessment becomes usable from every transport, which is the condition ADR-0012 and ADR-0013 both name. Donor → samples works end to end with M3 + this.
    • reel#10 shrinks to its Reel-side half (the tool schema's hard-coded "Sample" example): anchor: "Sample" is simply valid, and the grounding can render "kinds of Sample".
    • The GraphQL schema grows one interface per qualifying abstract class and one accessor each, NamedThing included unless the schema opts it out (Decision 5). Aperture derives collections from introspection and will list abstract collections; its deriveEdges and the result table need to handle interface-typed references (a follow-up on its side, gated on this landing in a certified pin — ADR-0029 honest degradation until then).
    • A concrete parent's own collection now includes its subclasses' rows (Decision 1): processes on brain bank lists every banking process. Clients that read total or counts on a concrete parent see larger numbers; release notes must say so.
    • A subclass row reached through a concrete parent shows only the parent's slots, and __typename says Process, not BankFreshBrain. That is the price of keeping field types unchanged; entityType names the subclass, and a client that needs the subclass's own slots must query it directly until the deferred change below.
    • Query cost: a closure resolution or abstract anchor is a UNION ALL over N tables (Postgres: an ANY over N types); on brain bank samples spans 33, and a root anchor spans every exposed class. Pagination applies after the union. Acceptable for paths that returned wrong answers or did not exist; measure.
    • The 56 build-time warnings on brain bank drop to zero.

    Alternatives considered¶

    • Union types. Simpler to generate, but a union has no fields of its own, so every selection of a shared slot needs a fragment per concrete kind (... on Blood { donor }, ×33). Rejected.
    • Interfaces but no abstract anchors. Fixes the references and the predicate flag but leaves "show me samples" unsayable and pushes the family/kind grounding entirely onto the planner. Rejected: the hierarchy is the server's fact to state.
    • Expose abstract classes as ordinary object types backed by no table. Every resolver would need the same closure logic ad hoc; an interface is the GraphQL construct for exactly this. Rejected.
    • Rename abstract classes concrete in the schema. Pushes a Mosaic limitation onto schema authors and changes the meaning of Sample. Rejected.
    • Abstract classes only (the ADR as first proposed). Leaves #241's concrete-parent nulls and every forward count/filter into an abstract range broken. Rejected 2026-11-10.
    • Skip a class whose closure is the entire exposed set (the original recommendation for NamedThing). A hard-coded policy guesses which roots are useless; a schema author knows. Replaced by the same rule for every class plus the Decision 5 opt-out annotations.

    Notes / open sub-questions¶

    • Deferred: a concrete parent as a GraphQL interface. Making Process itself an interface (implemented by Process's own object type and each subclass), so __typename names the subclass and subclass slots are reachable by fragment, would change the type of every field ranged on a concrete parent — a breaking change. Not decided here; it needs its own ADR if a client needs it.
    • Interface naming when a concrete class and an abstract class share a slot name with different ranges narrowed by slot_usage (e.g. DissectFixedBrain.inputs: CNSSection under Process.inputs: Sample): the interface field carries the abstract range; the implementing object type may narrow it (GraphQL allows covariant implementations). Confirm Strawberry emits it.
    • Mixins stay excluded (concrete_class_closure already skips them).
    • Amended 2026-11-10 (labadorf, #267 review): the question this section left open, whether a concrete parent's own collection (processes) lists subclass rows, is decided yes and moved into Decision 1.
    • Amended 2026-11-17 (labadorf, #276 review, ruling D1 = (a)): leaf-only names under a closure edge read as NULL. This replaces Decision 1's "a slot only some descendants have is UNKNOWN_SLOT" for the SDK where tree (both adapters). A nested where on a closure edge, forward or inverse, may name any field or reference edge that some class of C's concrete closure has. A row of a class lacking it reads the field as NULL (is_null true, every comparison false, so not {field = v} holds) and the edge as having no members (to-one and some false, none true). A name that no class of the closure has is still rejected as unknown. The rule applies at every nesting level: inside a nested reference's own where, the same rule applies against that reference's range closure. This keeps the #274 case (inputs some {hemisphere: L} → {a1}) and makes inverse edges, which kept the shared-slot rule before this note, consistent with forward ones. QuerySpec edge conditions and GraphQL's nested where input types still validate against the range's own slots (the manifest does not carry the hierarchy until Decisions 4–5 / #228), so there a leaf-only name remains UNKNOWN_SLOT.
    • Amended 2026-11-17 (labadorf, #276 review, ruling D2 = (a)): include_subclasses is public SDK API. MosaicClient.query and MosaicClient.count take include_subclasses: bool = True; False reads exactly the named class's rows (the pre-ADR-0014 behaviour) for code that walks one class at a time. The transports do not expose it. A migration transform's ctx.client (MigrationReadView) defaults it to False, so a concrete parent's transform never re-migrates its subclasses' rows unless it opts in with include_subclasses=True.
    • Amended 2026-11-17 (#276 review): one closure for storage and GraphQL. A concrete parent's collection resolves over its full concrete closure (SchemaRegistry.concrete_closure), and the GraphQL builder gives the parent's type entityType from that same closure, not only from subclasses that have their own GraphQL type. A row of a subclass without a GraphQL type is still a row of the parent: it is listed and counted through the parent, and entityType names its class. Today no concrete subclass of an exposed class can be unexposed; this rule is fixed now so that Decision 5's hippo_anchor: false opt-out hides the subclass's own accessor without hiding its rows from the parent or dropping entityType.
    • Corrected 2026-11-17 (labadorf, #278 review, choice 3): the clause above about hippo_anchor: false hiding a subclass's own accessor is wrong. Decision 5 stands as written: on a concrete class, hippo_anchor: false removes only QuerySpec anchoring, and the class's accessor and write surface stay. The rest of this amendment (one closure for the parent's collection and entityType) is unaffected.
    • Amended 2026-11-17 (labadorf, #276 review, ruling D3 = (a)): by-id lookup through a concrete parent is closure-aware. Decision 1's "accessor" covers the single get as well as the list: MosaicClient.get("Process", id) (and so GraphQL process(id:), REST and the typed client) returns a BankBrain row whose id it is given, with its concrete entity_type and full stored data, rendered in GraphQL as the parent type with entityType naming the subclass. get(..., include_subclasses=False) keeps the type-exact lookup, and a migration transform's ctx.client.get defaults to it. A leaf still does not answer for its parent's or a sibling's row, and an abstract class keeps the exact match until abstract anchors land (Decisions 2–5, #228).
    • Implementation notes 2026-11-17 (#228, Decisions 2–6; for ratification in review). Where the text above left a choice open or the 2026-11-17 amendments changed its premise:
    • Which classes are families. One rule, schema_typing.build_family_model, used by GraphQL and the manifest alike: an abstract, non-infrastructure class with at least one exposed concrete descendant. On brain bank that is ten families, NamedThing (86 kinds) included.
    • What the interface carries. "The slots induced on the abstract class" is read as the fields every kind stores alike — same name, kind, range, cardinality, target and enum. A slot a kind narrows differently (brain bank's format: SolidSampleFormat vs. LiquidSampleFormat) has no single GraphQL type and is on no interface; query the kind. Shared references are on the interface (Sample.donor, Sample.producedBy, counts for multivalued ones), so a shared field never needs a fragment. A family interface extends its nearest family ancestor's; a kind implements its most specific families.
    • Kind-only fields on the anchor read as NULL. Decision 3 said a subclass-only slot is UNKNOWN_SLOT on the abstract anchor; the D1 amendment made the same case read-as-NULL under a closure edge. The anchor now follows D1, so one rule holds everywhere: a field some kind has filters, orders and facets on the family (samples(where: {orientation: {eq: Coronal}})), reading NULL for kinds without it; a name no kind has stays unknown. It is in the family's GraphQL filter input and order enum, and in the manifest with only_kinds naming its kinds, so QuerySpec RelatedConditions into a family accept it too (closing the "until #228" gap in the D1 amendment). It is not an interface field: select it with ... on <Kind>.
    • include_subclasses on a family. False names a class with no rows, so it reads nothing (list, count, get); a migration transform's view therefore sees no family rows unless it opts in, which is the D2 rule.
    • By-id lookup. get("Sample", id) / sample(id:) returns the kind's row (the D3 rule, extended to families).
    • Search. search{Plural} on a family ranks over its kinds' FTS indexes; search_available is true when any kind has a searchable slot.
    • hippo_anchor: false on a concrete class removes only QuerySpec anchoring, as Decision 5 says; the "one closure" amendment above anticipates it hiding the class's own accessor. The implementation follows Decision 5's text — to be settled in review.
    • Accessor collisions. A family accessor that collides with another class's is not generated (build-time warning naming hippo_accessor); the interface is unaffected.
    • Ratified 2026-11-17 (labadorf, #278 review, "Choices to ratify"). The implementation notes above are settled as follows:
    • What a family interface carries: accepted as implemented. Only slots every kind stores alike are interface fields; a slot narrowed differently per kind (brain bank's format) stays off the interface and is reached through the kind's own type.
    • Kind-only fields on a family's own collection read as NULL: accepted. The D1 rule now applies everywhere and supersedes Decision 3's original UNKNOWN_SLOT for a subclass-only slot on the abstract anchor; a name no kind has (a misspelling) is still rejected. A projected row's data carries the NULL too (#281, fixed in #283).
    • hippo_anchor: false on a concrete class: Decision 5 as written. It removes only QuerySpec anchoring; the class's accessor stays. The "one closure" amendment's contrary clause is corrected in place (see its 2026-11-17 correction).
    • Accessor collisions: accepted for now. A colliding family accessor is not generated and the build warns; before 1.0 the warning becomes a build error (tracked in #280, under the 1.0 API freeze, #104).
    • Amended 2026-11-23 (labadorf, #289): lifecycle writes through a kind are closure-checked. Decision 6 says only that writes are unchanged for families, and nothing covers a lifecycle write addressed to a kind that is given another kind's id. Before this, setBloodAvailability(id: <Brain id>) reported success and changed nothing, and supersedeBlood(id: <Brain id>) superseded the Brain. The rule now follows D3. Availability (single and bulk), supersede and delete addressed to class K accept an id in concrete_class_closure(K), which is K's own rows plus its concrete subclasses' rows: setProcessAvailability(id: <BankBrain id>) acts on the BankBrain row, in its own class. A parent's, sibling's or unrelated class's id is refused before anything changes, with EntityKindMismatchError. That error is a subclass of EntityNotFoundError, so GraphQL reports NOT_FOUND, and the message names both classes. The check is in the SDK (set_availability_bulk, supersede_entity(..., entity_type=K), delete), so every transport gets it. supersede's replacement_id only has to exist, and may be of any kind, so a misclassified record can be superseded by a corrected record of another kind. Update and replace keep their exact-type rule (EntityTypeConflictError, GraphQL ENTITY_TYPE_CONFLICT): a subclass row cannot be updated through its parent's update…, because the payload has only the parent's slots.
